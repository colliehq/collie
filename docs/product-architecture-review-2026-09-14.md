## 产品判断

当前最值得继续改善的是同一条用户意图经过不同入口后，状态是否仍然一致。队列接受时冻结配置、会话执行租约、持久输入对账和明确的停止原因，已经构成可靠工作的基础。最近发现的普通路径问题集中在重复实现：界面认为检查“无法确认”，下一轮模型却收到“失败”；通过选择器换模型会刷新能力，通过设置面板换模型却不会。

这些分叉会让用户反复刷新页面、重选配置，或让 agent 修理没有证据表明存在的错误。统一状态判定和成功后的更新入口，比整体推倒架构更直接地改善使用体验。

## 已有机制与实际边界

| 工作流 | 当前机制 | 边界 |
| --- | --- | --- |
| 排队后再修改设置 | 接受请求时冻结运行预算和能力配置；运行时仍校验撤销的能力 | 冻结不代表忽略后续撤销，也不授予新权限 |
| 多入口打开同一会话 | 读盘前取得执行租约；在租约下重读会话 | 是防止互相覆盖的机制，不能推导为任何崩溃下都不会丢失数据 |
| 崩溃后恢复输入 | 根据持久日志确认已投递输入，剩余输入才释放回队列 | 无法确认外部动作是否执行时仍保留恢复栅栏 |
| 可选步骤走不通 | 与任务声明一致的非必需步骤可以记录后跳过 | 必须继续独立工作并说明遗漏；不能把主要目标静默放弃 |
| 长任务继续执行 | 普通交互不使用固定40轮停止；停止原因结构化记录 | 显式预算、模型调用上限、取消、权限和连续无进展仍会停止任务 |

## 建议的架构收敛

1. Python 主机回执复用一份权威分类，再让桌面、手机和模型输入保持同一语义。前端是否抽成共享资源，应由后续契约测试覆盖后决定。
2. 三个模型修改入口都从服务端确认的有效值更新当前模型和能力。能力读请求按代次接收，旧成功与旧失败都不能覆盖新结果。
3. 继续比较网页和终端的已接受队列重放规则，再考虑提取共享解析入口。现在已有防护，重构不得改变拒绝条件或已接受请求的权限。
