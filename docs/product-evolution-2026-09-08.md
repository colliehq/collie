# Collie 0.26：执行可靠性与订阅会话实验

本轮继续沿用“可选步骤受阻就跳过，主要目标无法安全推进时才询问”的用户偏好。
第一订阅窗口已用完，第二窗口的编码对照和工作流审阅已完成。两窗口共完成
166 次编码尝试并独立重评全部补丁。下文区分产品变化、实测与实验原型，不能将这些
不同版本的尝试合并成最终产品成功率。

官方只读用量记录显示：第一窗口达到 100%；第二窗口在 2026-09-08 00:21 PT 为
80%，周用量为 34%，额外付费关闭。本轮使用了两个额度窗口，并未耗尽整周额度，
也没有声称手动重置额度。后续离线回归和证据重评不调用模型。

## 产品判断

当前最影响顺畅使用的因素，是执行状态在不同层之间发生损失：工具结果被重复截断、
原生 formatter 报错后已有补丁无法正常交付、模型请求计数和实际调用不一致，以及
额度耗尽后任务仍频繁重试。继续扩充工具数量，对这些问题帮助有限。

0.26 优先修复这些边界。普通循环仍默认没有固定轮数上限；用户设置的时间、资源限制、
取消和未知操作的恢复检查继续生效。减少干预的目标是让宿主知道什么时候可以继续，
而不是把结果未知的操作当成没有发生。

从使用体验看，任务执行能力已有基础，但提交后的确定感仍不足：填写 Pack 检查后还
被要求重复填写、Continue 覆盖草稿、第二个窗口发送时丢消息，都迫使用户记住产品的
内部状态。本轮优先让正常操作直接完成，明确区分正在运行、已保存待执行和未确认
发送。已确认没有开始的请求可自动排队；无法确认是否接受的请求保留给用户核实，
不能为了减少点击重复执行。页面装饰的调整次于这些可复现的流程问题。

## 已提交的产品变化

| 问题 | 当前行为 | 主要实现 |
|---|---|---|
| 上下文已经选好，SDK 又把工具结果截成 2,000 字符 | SDK 接收上下文组合器选定的完整内容，避免丢失文件或检查结果的中段 | `claude_agent_sdk.py`、`claude_agent_worker.py` |
| 已知 provider 错误被误当成模型回答格式错误 | 保留经过验证的错误类别、订阅认证证据和已测用量；认证、计费错误不自动重试 | SDK provider 与 worker |
| 多请求 completion、拒绝发出的请求计数不一致 | 主循环、critic、摘要、Mission 共用实际请求计数规则 | `providers.py`、`loop.py`、`mission.py` |
| 原生结构化 formatter 失败后，工具调用或候选答案丢失 | 结构化模式恢复为显式选项；原生 formatter 重试关闭，失败进入宿主有界修复 | SDK provider 与 worker |
| 工具 stdout 可以伪装成“检查通过” | SWE 完成条件读取宿主执行收据，核对命令、调用身份、基线失败和修复后成功 | `tools.py`、`loop.py` |
| Codex 插话缺少当前 turn 身份，发送成功未必表示接受 | 提供 `expectedTurnId`，核对服务器接受的 turn；不重复发送可能已经送达的指令 | `codex_app_server_runner.py` |
| 点击 Continue 覆盖未发送文字、图片或 IDE 上下文 | 有草稿时保留给用户检查；空输入框仍直接继续 | `webui/index.html` |
| 手机宽度看不到正在操作的任务 | 当前标题保持可见，长标题省略显示 | `webui/index.html` |
| Claude 明确给出重置时间，Mission 却每分钟重试 | 保存进度和重置时间，在截止时间内持久等待，到点继续原目标 | SDK、Claude Code runner、Mission |
| 外部 worker 的恢复标记没有完整传到代码 Mission | 未完成工具、未知效果和缺失用量证据阻止自动续跑 | `primitives.py` |
| 截断恢复把输出限额留给下一次任务，或反而压低较大的设置值 | 临时增量在运行结束后恢复；用户原有的较大输出设置不会被降低 | `loop.py` |
| 等待卡片显示 epoch 或只显示时分秒 | 使用本地日期、时间和时区，简繁中文说明自动继续；不靠匹配模型回复中的英文短语显示时间 | `missionweb.py`、Web UI |
| Pack 已填写筛选检查，却仍要求第二条验证命令 | 桌面和手机端共用 Pack 的候选检查；单次 Required 验证、空检查和候选数量校验仍有效 | 桌面与手机 Web UI |
| 很早的一次格式错误耗尽整场任务的修复机会 | 有效回复恢复下一次独立错误的修复机会；连续错误和实际请求总量仍受限 | `loop.py` |
| UI 和收据显示推理强度，但 Claude Code worker 未收到设置 | 首次、继续会话及每个 Pack 候选传递所选 effort；Auto 由 CLI 决定 | runner、CLI、Web、Pack |
| 旧工具调用经过加载转换后被误判成新历史 | 比较加载后的前缀但保留原始记录；新输入的额外字段不会被忽略 | `sessions.py` |
| 页面尚未发现任务正在运行，发送后被拒绝并丢掉输入 | 明确未开始的请求自动进入原任务队列，保留提交时的设置和附件 | Web UI |
| 切换任务、刷新或保存响应延迟覆盖新草稿 | 未确认请求单独保留，同文不同附件不合并，重发沿用原请求编号；只发图片也可恢复 | Web UI |
| 后台已保存，但界面仍要求用户重发 | 队列收据按请求编号自动消除不确定提示，不再发起第二次提交 | Web UI |
| 附件超过浏览器存储额度，恢复时悄悄省略文件 | 明确标记缺失附件，重新附加或由用户明确选择省略后才能发送 | Web UI |

额度等待仅使用官方流中的已拒绝窗口和明确 reset 字段，不解析模型回复中的日期。
Claude Code 已完成且有成功收据的文件编辑可以保留并继续；未配对、失败、重复或未知
工具记录仍要求核实。停止、超时、截断、会话身份冲突不会借此变成自动恢复。
前台单次运行会返回等待原因；跨额度窗口持续运行由 Mission 负责。

请求恢复使用同一标签页的 sessionStorage，可跨刷新保留；不保证关闭标签页或清理
浏览器数据后的恢复。已上传附件不代表模型任务已开始。未确认的流不会自动重放，
但队列返回同一请求编号时会自动解除提示。新任务恢复也带回原设置，Pack 自动应用
授权仍不记忆。详情与边界测试见证据包中的 `product-validation/workflow-review.md`。

## 第一窗口的实验结论

截至第二窗口开始前，本轮有 **68 次原生编码尝试、16 次统一传输适配尝试**。所有
84 份候选都从冻结初始文件重新应用补丁，并在模型工作区外独立评分。失败尝试也保留。
它们属于多个逐步修复的版本，不能把总数直接当成某个最终产品的成功率。

两道任务分别覆盖版本化分页游标和事件投影账本。比较使用 `claude-opus-5`、高推理
强度，设置明确实验资源上限；这些上限是测试条件，不是产品默认对话上限。
原生 CLI 的 48-turn 限制不等于 Collie 侧的物理请求记账；两者的原生计数不能直接
当作相同的调用次数。统一传输轨道另由共享 sidecar 执行物理请求限制。

### 默认响应协议

最后一组同步对照采用相同源码 `9e26c142`、两题各两次：

| 协议 | 独立补丁检查通过 | 正常结束 |
|---|---:|---:|
| plain envelope | 4 / 4 | 4 / 4 |
| SDK 原生 structured formatter | 4 / 4 | 2 / 4 |

两个结构化失败都发生在已经得到正确补丁之后，宿主一次格式修复仍未正常结束。
因此目前没有依据把原生结构化模式设为默认。它也不能仅因补丁正确就被计为成功交付。
较早的协议冲突版本、formatter 重试版本及其失败记录均保留，不用新结果覆盖。

### 持久 SDK 会话

公共代码审阅对话做了 3 组、每组 6 轮，比较每轮新建 SDK 调用和复用
`ClaudeSDKClient`。36 次请求全部完成；排除每组首轮后：

| 指标 | 每轮新调用 | 持久会话 |
|---|---:|---:|
| follow-up 中有 cache read 的次数 | 0 / 15 | 15 / 15 |
| follow-up cache write 总量 | 175,835 | 17,543 |
| follow-up cache read 总量 | 0 | 175,241 |

这组对话的 cache write 下降约 90.0%，但没有执行宿主工具，不能证明真实编码成功率、
成本或速度同样改善；订阅返回的 token / API 等价金额也不是实际账单。

持久传输原型仍在独立实验 checkout，产品工厂不选择它。它只能复用严格追加的历史；
摘要、旧工具结果省略、工具或系统配置改变时必须重建会话，不能继续保留宿主已删除的
上下文。未确认的进程清理会阻止启动替代 worker。真实多轮 worker 和新编码任务的
对照在第二窗口完成，结果见下文。原型仍不进入产品默认路径。

随后用真实上下文组合器和脚本回复做了零模型机制检查：30 步工具交流中，默认省略
策略造成 22 次历史改写、共打开 23 个会话，最长连续 8 步。保留工具历史的机制对照
可连续 30 步使用一个会话。这证明不能把六轮对话的缓存收益外推到长任务。第二窗口
增加独立的上下文策略对照；强制溢出恢复、图片处理和语义摘要仍由原有宿主逻辑决定。

### 其他 harness

统一传输轨道使用固定的 Pi、Hermes、Prime 和 Collie 适配器，底层都是同一个官方
SDK sidecar；这比较适配后的循环、提示和工具行为，不代表各产品原生体验的排名。
16 份补丁都通过离线独立检查；其中 15 次是有效完成，另一次 Prime 的请求账本不完整，
仍保留为无效实验。后来的补丁评分不能修复缺失的原始调用证据。后续控制器已增加
清理前保存、且不含提示内容的请求收据。

## 运行时版本修正

第一窗口的原生 Claude Code arm 使用 2.1.221；SDK 0.2.136 实际优先选择自身捆绑的
2.1.228。Windows 有版本及二进制 SHA-256 检查；最初的 Linux sidecar 检查仅记录
版本。过去仅写原生 CLI 版本的实验清单不足以证明 SDK 使用同一版本，应结合单独
运行时审计读取。

这是运行后的安装检查，不是对每个历史请求的逐一运行时证明。旧记录不重写。
第二窗口的原生对照在各清单保存 CLI 与 SDK 的 2.1.228 版本和二进制哈希。统一传输
沿用固定 Docker 镜像；其历史清单没有同样的逐实验 inventory。随后另对该 sidecar
镜像记录 Linux 二进制哈希和时间，属于运行后镜像检查，不是每次请求的运行时证明。

### 持久会话为什么一度更差

相同实验源码 `31d0b0c7`、plain 回复协议：

| 上下文策略 | 非持久：补丁正确 / 正常结束 | 持久：补丁正确 / 正常结束 |
|---|---:|---:|
| 产品默认工具历史省略 | 6/6 · 6/6 | 3/6 · 3/6 |
| 保留工具历史的机制对照 | 6/6 · 6/6 | 5/6 · 2/6 |

持久失败是回复协议漂移，不是“缓存命中即成功”。逐条记录显示，早先格式错误修复成功、
中间已完成多个有效工具步骤后，第二个独立格式错误仍直接结束任务，因为修复计数是
整场运行共享的一次机会。产品现改为连续错误计数，有效回复后恢复机会；总修复次数
仍记录，物理请求和 token 上限不变。
“正常结束”按各执行器自己的结束协议判定；Collie 的宿主回复协议和持久进程清理
失败是自身产品失败，原生 Claude Code 没有同一层协议，不能解释成两组相同内部
检查项的通过率。错误细分类由运行后错误文字和结构化终态辅助归类，未分类错误
仍留在总数中；不会用这些诊断标签授权重试或恢复。

新登记的同步 A/B 每组 6 次：旧版 2/6 补丁正确、1/6 正常结束，其中 4 次协议失败、
1 次 provider 500；仅改修复计数的版本为 **6/6 正确且正常结束**。不能把那次服务错误
算作该修复解决的问题。零模型回归还覆盖服务重试不恢复格式额度、总请求预算仍阻断。

### 缓存收益和默认值选择

再以修复后的相同源码 `310a3418`、完整工具历史，比较非持久、持久、每轮重申格式的
持久方式。两题各三次，三组均 6/6 正确且正常结束；全部进程清理有确认收据。

| 新题 | 非持久 cache write 中位数 | 持久 | 持久 + 格式提醒 |
|---|---:|---:|---:|
| 容量预留账本 | 304,409 | 62,397 | 66,925 |
| 路径规则优先级 | 215,901 | 88,754 | 65,183 |

格式提醒组有一次连续 20 轮复用一个原生会话，但其他运行仍需重建。非持久使用平铺
历史、持久使用原生轮次，两者不仅缓存方式不同；并发审阅也会影响时间。这里支持
“值得继续开发持久传输”，不支持稳定速度排名或真实账单节省比例。产品继续采用已
验证的默认路径，实验源码和重建补丁随证据保存。
每格只有三次，持久与提醒组分布明显重叠：账本 cache write 分别为 49,221–100,330
和 29,574–98,617；路径题为 73,948–99,877 和 45,088–117,529。20 轮完整复用是
对应格三次中的一次，不能证明提醒稳定优于未加提醒的持久会话。
