# 2026-09-07：高并发 Claude 订阅实验

这轮找到三个值得优先解决的问题：Collie 的原生 SDK 路径报告了明显更多的缓存新建 token；正确代码仍可能伴随收尾协议错误；各个 harness 都可能漏掉跨多个入口的同一条要求。现有样本不足以证明哪个产品整体更强。

本轮冻结 Collie **0.25.0 / `8577c10a33370bf84ae9cf953db64354be92a30d`**，使用 Claude Code 订阅完成 **90 次编码尝试、8 组真实网页多轮流程、6 份开源源码审阅**。90 次中只有 60 次属于两条主要对比，其余是校准、消融和事后诊断。实验期间没有修改被测产品实现。

这是探索性本地任务集，`publishable: false`。它不满足[正式协议](harness-benchmark.md)所要求的全部控制条件，不是 SWE-bench 分数，也不是 harness 效果的因果估计。特别是本实验纳入 Prime 的适配循环，不改变正式协议对参赛产品和准入的规定。

2026-09-07 10:53 PT，账户 API 报告 5 小时额度使用 0%、周额度使用 22%；11:33 PT 首次观察到 5 小时额度 100%、周额度 39%，11:40 PT 复查相同。账户为 Max 20x，额外付费用量关闭。额度变化属于整个账户，不能全部归因于本实验。

**已经用满当时可用的 5 小时窗口，没有用完周额度。** 周额度还剩 61%，但会话窗口到当天 15:50 PT 才重置，晚于用户指定的 13:00 PT 截止和本周重置时间。达到 100% 后设置 STOP，不再启动模型任务。

用户进一步要求核实能否提前重置。官方资料仍说明会话额度每 5 小时重置，周额度独立按固定时间重置；继续使用的额外 usage credits 单独收费。没有查到公开的免费手动提前重置机制。当前浏览器连接不可用，因此没有核实账户页面是否存在个别赠送活动，也没有声称账户绝无该入口。没有执行账户重置、购买额度或开启额外付费。[Max 官方说明](https://support.claude.com/en/articles/11049741-what-is-the-max-plan)、[usage credits 官方说明](https://support.claude.com/en/articles/12429409-manage-usage-credits-for-paid-claude-plans)

## 原生产品结果：24 次

“代码正确”由外部 grader 判断；“正常结束”要求没有 worker/protocol 错误。耗时统计包含该轨道全部尝试，不只挑成功样本。

| 路径 | 代码正确 | 正常结束 | 全部尝试耗时中位数 | 缓存新建 token 合计 |
| --- | ---: | ---: | ---: | ---: |
| Claude Code | 9/12 | 12/12 | 163.6 秒 | 304,047 |
| Collie | 10/12 | 11/12 | 196.8 秒 | 4,391,205 |

| 任务 | Claude Code 正确 | Collie 正确 | Claude Code 耗时中位数 | Collie 耗时中位数 |
| --- | ---: | ---: | ---: | ---: |
| 持久收件箱、租约与修订 | 0/3 | 1/3 | 161.6 秒 | 270.5 秒 |
| 分层配置与来源追踪 | 3/3 | 3/3 | 138.5 秒 | 168.0 秒 |
| 缓存、过期读取与快照 | 3/3 | 3/3* | 167.6 秒 | 186.1 秒 |
| 事务目录补丁与回滚 | 3/3 | 3/3 | 174.0 秒 | 235.2 秒 |

*Collie 的一次缓存尝试留下了通过 grader 的补丁，但在 29 次模型请求后出现 `HTTP 422 response_contract_error`，一次结构化输出修复后仍失败。它应记作“代码正确、运行异常”，不是共享基础设施失效，也不能从分母中删除。

![原生轨道耗时与缓存](https://raw.githubusercontent.com/colliehq/collie/v0.27.0/bench/experiments/2026-09-07/native-comparison.png)

Collie 报告的缓存新建 token 总量约为直接 Claude Code 的 **14.4 倍**；各任务的中位数也有同方向差异。这是需要调查的效率信号，不能解释成实际账单贵 14.4 倍，也不能把缓存新建 token 当作全部输入 token。当前 Opus 5 的 API 等效价格映射不可靠，因此不用美元估值排名。

每个 arm 的 9 个组合为：配置、audit request ID、circuit breaker 各 1 次，缓存、收件箱、事务补丁各 2 次。四个 arm 的代码正确率相同，8 次收件箱尝试都漏掉了同一条明确要求。

## 失败诊断和网页体验

收件箱的共同漏项是 `Inbox.get("")` 没有抛出 `ValidationError`。原始要求明确规定 key/owner 必须是非空白字符串，读入口同样适用。多数候选代码补了写入和租约入口，却漏了只读入口。这个失败属于要求遗漏，不能放宽评分来消除。

只给 Collie 增加 bash 工具后，缓存 2/2 正确，收件箱仍 0/2；对应耗时中位数为 169.2 秒、165.7 秒。样本很小，工具消融没有解决要求遗漏，也没有作为产品默认行为发布。

观察上述失败后，在原始提示末尾增加“结束前逐条核对要求是否覆盖所有公开入口，包括只读方法及一致的参数校验”。用原始工作区重新开始，未向模型提供隐藏测试或失败输出。原生 Claude Code、Collie 各 1/1 通过；统一传输四个 arm 各 1/1 通过。该提示是**事后选择**，不是盲测或独立确认。下一步应在未见过的任务上检验通用覆盖检查，而不是在产品里写入本题答案。

8 组网页流程全部完成两阶段代码修改和同线程追问，16 个代码阶段的 **1,328 次外部断言**全部通过；本轮没有记录到移动宽度横向溢出或流程错误。覆盖任务是区间合并、配置合并，包含需求变更、参数拒绝、输入不可变和深拷贝隔离。这说明这些路径可用，不等于全 UI 审美审阅、所有设备兼容性或长时间恢复压力测试都已完成。

## 评分修正与证据完整性

1. 最初 6 次 Collie 校准因缺少模型请求授权，在 0 次模型调用处失败；补齐持久请求台账后进行新的配对校准。旧失败保留，未计入主要能力分数。
2. 大型 grader 超过 Windows 命令行长度限制后，改为宿主脚本文件加 `python -I`，评分要求未改变。
3. 任务作者的 grader 通过 `sys.exit(main())` 正常结束，旧评分包装器却在其后写成功标记，造成假失败。修正可信 grader 的结尾后，对原来 4 个配置候选统一重新评分。之后准入同时验证真正使用的 marker grader。
4. 事务补丁要求按应用顺序返回路径，却没有要求 tuple；原评分额外强制 tuple，误拒了 list。修正为比较 `tuple(report.paths())`，保留顺序约束。原生 6 次、统一传输 8 次候选统一重评，全部通过。原始提示、fixture、候选补丁未改，无模型重跑。新旧 grader 哈希保留。
5. 缓存任务明确要求新增 `snapshot.py`；旧准入器只允许参考实现包含已有文件。修正准入验证，不在实际初始工作区添加占位文件。
6. 汇总时把上述 Collie 422 错误从笼统的 infrastructure 标签纠正为 harness/protocol 错误，同时保留代码通过和运行异常两个维度。

90 份候选补丁均与原始记录的 SHA-256 一致。对原结果的修正另存，不覆盖原始结果；所有失败保留。归档包含完整候选补丁、明确的任务/参考实现/隐藏 grader、脱敏结果、评分修正、冻结脚本和校验清单，不包含原始登录凭据或完整对话 receipts。

导出后独立重建并重新评分全部 60 个主要候选，结果与表格一致；七个原始/诊断任务的 14 次 baseline/gold 校验全部通过。三条复跑路径通过准备检查，统一传输路径通过 Docker 版本和隔离配置预检。以上验证均为 0 次模型调用，没有声称重新运行了一遍模型实验。

## 对下一版的建议

| 优先级 | 证据与原因 | 可验收的下一步 |
| --- | --- | --- |
| P0 | 正确补丁仍因结构化收尾失败而异常结束 | 固定 422 失败 trace，建立不重复执行已完成工具的恢复测试；UI 同时展示已保存成果和执行错误 |
| P0 | 原生 SDK 缓存新建量明显偏高 | 比较稳定提示前缀、工具结果批处理、持有推理进程的方案；在新任务上测请求数、缓存读写、首响应、总耗时与取消延迟 |
| P1 | 多个 harness 漏掉跨入口要求；shell 未解决 | 用未见任务验证通用要求覆盖检查，要求检查能减少漏项且不显著增加短任务延迟 |
| P1 | 已通过的网页流程只覆盖少数短任务 | 增补运行中插话、重启恢复、工具结果未知、上下文压缩后约束保留、额度耗尽后恢复的故障注入 |
| P1 | 用户希望减少打断 | 可选失败自动跳过；主要目标确实无法继续时才提示；清楚区分完成、保留成果后暂停、用户取消和失败 |

源码上，`harness/claude_agent_sdk.py` 的 `_payload` 序列化历史和工具，`_run_worker` 启动自有短生命周期进程；`harness/claude_agent_worker.py` 以 `max_turns=1`、关闭会话持久化并调用 `sdk.query` 完成每次推理。这支持调查输入稳定性和进程复用，但**不能证明启动进程本身导致了缓存未命中**。优化必须保留现有授权、取消、请求台账和恢复语义。

六份 Claude 源码审阅还提出了 steering、截断后参数恢复、验证命令识别等静态线索；它们尚未逐项独立复现，不计作本轮已确认缺陷或已完成修复。参考实现的固定轮数上限也不应照搬为 Collie 默认停止条件。
